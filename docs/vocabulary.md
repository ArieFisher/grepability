# Vocabulary

One term per concept, used in every document, comment, test name, commit message, and result file in this repository. The **Retired** column lists the words that the term replaces; a line added to a markdown file never contains one of them. The table is the machine form: a check reads the Retired column from this file and holds no copy of its own.

## The experiment

| Term                   | Meaning                                                                                                                                                                                                                                                                                                                        | Retired                                                |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| grepability            | A code metric of how easily one can find use text-search tools like `grep`, `ripgrep`, or search bars to find search terms                                                                                                                                                                                                     | grep-ability, greppability, searchability, findability |
| conceptual grepability | A metric of how well a code base is organized so that text-search tools (like grep, ripgrep, etc.) can find **all relevant code and comments** for **core concepts** of a codebase.                                                                                                                                            |                                                        |
| concept                | One idea in the codebase that the experiment tracks. Each concept has an id, a definition, a search term, and seeds. The concept configuration holds the list.                                                                                                                                                                 | topic, notion, theme                                   |
| search score           | The measurement of grepability: one search per concept, scored against the ground truth. For one concept in one version it is the harmonic mean of find rate and term distinctiveness. The search-score script runs the searches.                                                                                                                                                                                                   | measure 1, experiment 1, test 1, the search measure    |
| agent score            | The measurement of the *effect* of grepability: an agent does each task in each version, and the scoring script checks what it found or changed. For one concept in one version it is the success rate over the runs of every task on the concept.                                                                                                                                                                               | measure 2, experiment 2, test 2, the agent measure     |
| codebase               | The code the experiment runs on: one repository pinned to one commit, as the codebase configuration states.                                                                                                                                                                                                                    | target, library, project under test, subject           |
| published codebase     | The codebase as published, at its pinned commit.                                                                                                                                                                                                                                                                               | arm A, baseline codebase, original codebase            |
| proposed codebase      | The published codebase with each concept reworded to its search term, with every line number unchanged.                                                                                                                                                                                                                        | arm B, candidate codebase, treated codebase            |
| snapshot commit        | The one commit each run copy starts from. The scoring script diffs the run copy against it, so edits the agent staged or committed still count.                                                                                                                                                                                | base commit, initial commit, starting commit           |
| codebase configuration | The file that states which code the experiment runs on and how to check it: the repository, the commit, the corpus, the compile command, the type check commands, and the test settings (test folder, files to skip, test command, rerun command, and title separator). Every script reads it, so no script holds a fact about the codebase itself. | test run configuration, codebase file, codebase config |
| corpus                 | The files of the codebase that the experiment covers. Ground truth, searches, and scoring cover only these files.                                                                                                                                                                                                              | source tree, source files                              |
| compile | The codebase's own step that turns its source into the compiled code and declarations that its type tests import. Each version compiles from its own source, so the type check of a version reads that version's declarations. | build step, distribution build, dist |
| search term            | The one regular expression that stands for a concept in a search. The search-score script searches each version with it for the search score. The proposed codebase build rewords the concept so that the search term matches every line of the concept.                                                                       | search pattern, grep pattern, query, keyword           |
| forms                  | The wider regular expression that matches every wording of a concept in the published codebase. The scoring script uses it to pick the lines a rename task had to change.                                                                                                                                                      | variants, aliases, spellings                           |
| name | An identifier in the code: a variable, parameter, property, function, or type. The type checker resolves each use of a name to the declaration it refers to, so names are the part of the corpus the type checker covers. Comments and strings are text, not names. | identifier, symbol name, variable name |
| seed                   | A name in the published codebase's code, written as file, line, and name. The type checker starts from it to find the concept's references.                                                                                                                                                                                    | anchor, root symbol, starting point                    |
| control concept        | A concept whose wording is already consistent, so the proposed codebase build leaves it unchanged. It shows what both scores give when there is nothing to fix.                                                                                                                                                                | baseline concept, placebo                              |
| version                | One of the two codebases the experiment compares: the published codebase or the proposed codebase. Both scores cover each version.                                                                                                                                                                                             | arm, variant, condition, treatment, branch             |
| rename                 | A proposed codebase edit to a name. The proposed codebase build replaces every location the type checker returns for the name, so every reference changes and nothing else does.                                                                                                                                               | symbol rename, refactor                                |
| wording edit           | A proposed codebase edit that replaces exact text on one line of a comment or string.                                                                                                                                                                                                                                          | comment edit, text edit, rewording                     |

## Ground truth

| Term | Meaning | Retired |
|---|---|---|
| ground truth | The set of lines in the published codebase where each concept appears. Name lines come from the type checker; text lines come from the reviewers. | truth set, gold standard, answer key, expected lines |
| name line | A ground truth line that holds a reference the type checker found from a seed. | identifier line, symbol line, code line |
| text line | A ground truth line that holds a comment or string the reviewers tagged. | comment line, string line, prose line |
| review sheet | The list of every comment line and string line in the corpus, one row each, with an empty column for concept ids. | candidate list, line list, worksheet |
| reviewer | A person or an AI stand-in that tags the review sheet. Each reviewer saves a tagged copy under their own name. | annotator, rater, labeler, judge |
| tag | A concept id a reviewer writes on a row of the review sheet. | label, annotation, vote, mark |
| agreement | Rows where every reviewer gave the same tag for a concept. Cohen's kappa summarizes it for two reviewers. | consensus, inter-rater reliability, overlap |
| disagreement | A row and concept that some reviewers tagged and others did not. The ground truth script lists these for a person to decide. | conflict, split, mismatch |
| adjudication | A yes or no on each disagreement, from a person or an AI stand-in. Until every disagreement has one, the ground truth is provisional. | resolution, arbitration, tie-break |
| adjudicator | The person or AI stand-in who gave an adjudication. The adjudication file records one per decided row, the ground truth lists them, and every result file prints them. | arbiter, tie-breaker, decider |
| provisional | The state of a ground truth with at least one disagreement that has no adjudication. Every result file records whether its truth is provisional. | draft, preliminary, incomplete, tentative |
| line kind | The kind of text a ground truth line holds: one of the kinds in the line kinds table. A text line takes the kind the review sheet records for it. A name line takes the kind of the declaration its name refers to, as the type checker reports it. A line that holds two kinds has both. | line type, line category, token kind |

### Line kinds

The TypeScript kinds column is the machine form of the mapping from a declaration kind to a line kind. A declaration kind the column lacks maps to `other`.

| Kind | Meaning | TypeScript kinds | Retired |
|---|---|---|---|
| comment | A line that holds a comment. | | remark |
| string | A line that holds a string and no comment. | | text literal |
| property | A name of a property of an object, a class, or a type, including a class field and an accessor. | property, getter, setter, enum member | attribute |
| parameter | A name of a function or method parameter. | parameter | |
| variable | A name of a variable. | var, let, const, local var, using, await using | |
| function | A name of a function, a method, or a constructor. | function, local function, method, constructor | procedure |
| type | A name of a type, an interface, a class, an enum, or a type parameter. | type, interface, class, local class, enum, type parameter | type name, class name |
| other | A name whose declaration kind the TypeScript kinds column lacks. | | misc |

## Agent runs

| Term | Meaning | Retired |
|---|---|---|
| agent | The coding agent command line. A local run starts it once per task in a run copy with a fixed model, budget, time cap, and tool allowlist. A cloud run starts it in a routine, which fixes the model; the budget, time cap, and tool allowlist do not apply. | AI, assistant, model, bot, coding agent |
| task | One prompt the agent gets, tied to one concept. A find task requires a list of lines in the reply. An edit task requires a change to the code. | job, prompt, exercise, problem |
| find task | A task scored on the lines the agent lists in its reply. | search task, list task, locate task |
| edit task | A task scored on the lines the agent changed, plus the type check, the tests, and the hidden test when the task has one. | change task, modify task, refactor task |
| rename task | The edit task that has the agent rename a concept everywhere: every name in code and every comment. It is scored on the target lines. The proposed codebase build edit to a name is a rename, not a rename task. | rename job, renaming exercise |
| required lines | For an edit task, the lines the agent had to change, fixed in the task configuration. | must-change lines, expected edits |
| target lines | For a rename task, the lines the agent had to change: the concept's name lines plus text lines whose wording matches the forms in that version. | expected lines, rename lines |
| cell | One task in one version. The run script spreads runs round-robin over cells, so drift in the model service over time reaches every cell alike. | condition, group, bucket, task-version pair |
| run | One execution of the agent on one task in one version, with a random id. A local run executes on this machine in its own run copy. A cloud run executes in a routine. | trial, attempt, execution, session, sample |
| run copy | The fresh copy of a version made for one run. It has the same folder name in every run and links to shared dependencies. A cloud run gets its run copy when the collect script gathers the run, with the run branch's changes applied. | sandbox, workspace, checkout, working copy |
| key | The file that maps each run id to its version and task. The summary script reads it last, after the blind review sheet is answered. The scoring script reads it to score each run, and writes no version into any file a person opens. | mapping, lookup, index, legend |
| blind review | A person's pass over run diffs with no version shown, to mark wrong edits before the key is read. | blinded review, masked review |
| blind review sheet | The list of every run, one row each, in shuffled order with no version. The person doing the blind review writes yes or no in the wrong_edits column. A rescore keeps the rows and answers already there and adds only new runs. | judging sheet, blind sheet, review form |
| wrong edit | An edit in a run's diff that the person doing the blind review marks as incorrect or not asked for. The summary counts the runs marked yes next to the runs answered; the count leaves success unchanged. | bad edit, unexpected edit, bad change |
| cloud run | A run that executes in a routine on a run repository, in place of this machine. It reports the diff and the final reply, and no cost, time, turns, or tool counts. | remote run, web run, hosted run |
| routine | A saved claude.ai configuration of a prompt, a repository, and an API trigger. One routine exists per task and version; the fire script starts a cloud run by calling its trigger. | scheduled task, automation, job, workflow |
| run repository | The private GitHub repository that holds one version for cloud runs: the version's files and the start hook, as one commit. Its name shows no version. | cloud repository, mirror, copy of the version |
| run branch | The branch that a cloud run pushes its changes and reply file to. Its name is the run id behind the run branch prefix in the task configuration. | result branch, output branch, answer branch |
| reply file | The file in which a cloud run writes its final reply, because the fire request returns no reply. The collect script reads it into the run's final reply. | answer file, output file, result file |
| start hook | The small file in each run repository that installs dependencies and compiles when a cloud run starts, so the agent can run the type check and the tests. Both versions carry the same hook. | setup script, bootstrap, init script |
| pending run | A fired cloud run whose run branch has not appeared. After the pending limit in the task configuration, the collect script records it as a failed run with no changes. | queued run, waiting run, in-flight run |
| transcript | The agent's full event stream for one run, as newline-delimited JSON. | log, trace, session log, output |
| final reply | The agent's last message in a run. The scoring script scores find tasks on its last fenced block. | final answer, response, result text, output |
| baseline | The type check and test results of a version before any agent touches it. A test that fails in a baseline never counts as a regression. | reference results, control results, original results |
| hidden test | An acceptance test copied into a run copy after the agent finishes, so the agent cannot read it during the run. | hidden acceptance test, secret test, holdout test |
| regression | A test that passed in the baseline and fails in a run, after a rerun confirms the failure, or that the run removed. The scoring script matches tests by test title within each test file and follows a renamed test to its new title, so a renamed test is judged by its own result and a removed test counts. A failing test under a new title that belongs to no renamed test is a new test, not a regression. | breakage, failure, broken test |
| test title | The name the test command prints for one test: the test file name, the title separator in the codebase configuration, then the name the test itself declares. Baselines and run results record each test under its test title. | test name, test label, test id |
| test declaration | The line in a test file that declares one test and the name its test title ends with. The declaration pattern in the codebase configuration captures the name; the scoring script skips a name built from a template expression, because the test command prints the expression's value. | test definition, test header |
| hunk | One block of changed lines in a diff, under a header line that holds the block's start line and its counts of removed and added lines. The script that saves a run's diff writes no unchanged lines around each hunk. | change block, block of changed lines, diff chunk |
| lost title | A test title that the baseline holds and a run's results lack, under the title itself or, for a renamed test, under its new title. A lost title belongs to a removed test, a test file that stopped partway in the run, or a rename the scoring script cannot pair from the run's diff. | missing test, vanished test, dropped title |
| new title | A test title that a run's results hold and the baseline lacks. | added title, extra test, unknown test |
| renamed test | A test whose test title a run changed. The scoring script reads renamed tests from the run's diff: within each hunk of a test file, it pairs the removed test declarations in order with the added ones, when the two counts are equal. The scoring script makes no pairs from a hunk with unequal counts or across two hunks, so a test the agent both moved and renamed keeps its old title as a lost title. A test the agent removed pairs as a rename with an unrelated test the agent added in the same hunk. | retitled test, moved test |
| removed test | A lost title that fails its rerun. The scoring script reruns the test file's lost titles once each, in order. A pass means the test file stopped partway, and the run records it; the failed reruns before the pass count as removed tests. When five reruns fail, every lost title in the test file counts as a removed test. Each removed test is a regression. | deleted test, dropped test |
| flaky | A test that both passes and fails across reruns of the same run copy. Flaky tests count as neither regressions nor differences. | unstable, nondeterministic, intermittent |

## Scores

| Term | Meaning | Retired |
|---|---|---|
| hit | A line a search returned. | match, result, occurrence |
| found | A hit, or a listed line, that is in the ground truth. | true positive, correct hit |
| miss | A ground truth line that a search or an agent reply did not include. The search-score script leaves locked lines out of a search's misses. The published codebase's misses are the worklist for the proposed codebase. | missed line, false negative, gap, omission |
| locked line | A line that no rename or wording edit can change without changing behavior. It takes one of two forms: a ground truth line that no edit can make the search term match, or a hit outside the ground truth that no edit can stop the search term from matching. No edit can change four kinds of text: a name the standard library declares, a public name that callers use, a string the program outputs or compares at runtime, and a file path or a URL. A comment is locked only when its only concept wording, or its only text the search term matches, names a name of the first two kinds. A code line with no wording of the concept is locked with the reason "no wording on the line". Each concept in the concept configuration holds its locked lines, each with the text that locks it and a reason. The search-score script reads the lists and stops when an entry's text is not on its line in either version. | fixed line, unchangeable line, excluded line, out-of-scope line |
| find rate | Found lines divided by ground truth lines: of every line where the concept appears, the share a search or an agent reply included. The search-score script leaves locked lines out of both counts. | recall, coverage, completeness, sensitivity, hit rate |
| term distinctiveness | Found lines divided by hits: of every line a search term returned, the share that belongs to the concept. The search-score script leaves locked lines out of both counts. It is a property of the search term in one version. A low value has two causes. Search term overload: the codebase holds the same word for a second thing that could carry its own name, and a rename fixes it. Structural overlap: the codebase holds distinct concepts that share language, such as rate, annual rate, and effective rate, and the codebase is structurally indistinct for that term. | precision, accuracy, purity, positive predictive value |
| success | A run that met every condition of its task: no misses, and for an edit task a passing type check, no regressions, and a passing hidden test when there is one. An edit run with a test file that stopped partway has unknown success, because the scoring script holds no result for the tests after the stop. The summary script and the results-table script leave such a run out of the success count, the interval, p, and the agent score until a rescore gives it a verdict. | pass, win, completion, correct run |
| interval | The Wilson 95% interval around a success count. | confidence interval, error bar, range, margin |
| p | The two-sided Fisher exact test between published codebase and proposed codebase success counts for one task. | p-value, significance, probability |
| results table | The table of each concept's search score and agent score in each version, with the change for each score, the find rate and term distinctiveness behind the search score, and the overall row. The results-table script writes it. | results matrix, scorecard, summary table |
| change | A score in the proposed codebase minus the same score in the published codebase, in percentage points. | delta, difference, improvement, lift |
| overall row | The results table row that combines every concept except the control concept. Its search score is the mean over those concepts, so each concept counts once. Its agent score pools their runs, so each run counts once. A concept with no search score in a version leaves that version's overall search score empty, so both versions average the same concepts. | total row, aggregate, summary row |

## Words kept literal

- **line** is always a line of a file, written as path and number separated by a colon. A line of prose in a document is a sentence.
- **search** is always one ripgrep run with one search term. Grep, ripgrep, and search are not interchangeable in prose: "search" stands for the operation, "ripgrep" stands for the tool.
- **test** without a qualifier means one of the codebase's own tests. The scripts' own tests are "unit tests".
- **copy** never appears without a qualifier. Write "run copy" or "version".

## Applied to Ky

The current codebase is Ky, pinned to the commit in the codebase configuration. The corpus is every TypeScript file under its source folder. The five concepts are `retry count`, `retry delay`, `progress callback`, `caller abort`, and `jitter`, with jitter as the control concept.
